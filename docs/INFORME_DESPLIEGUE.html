GitHub Actions

Resumen

Se desplegó la versión v1.0.0 publicada en GitHub Releases, se verificó su funcionamiento y se documentó el procedimiento completo. Después se preparó la versión v1.1.0, que agrega el registro de productos, y se ejecutó un ejercicio de fallo simulado con recuperación a v1.0.0. La automatización se implementó en .github/workflows/deploy.yml, usando el runner de GitHub Actions como entorno de destino con un servicio SSH local para evidenciar la transferencia y la ejecución remota.

Alcance declarado

El entorno de destino es el runner ubuntu-latest de GitHub Actions. El workflow levanta un servidor SSH local (127.0.0.1) y transfiere el paquete con scp para producir evidencia real de transferencia y ejecución. No se utilizó una máquina virtual externa; el mismo workflow puede apuntar a un servidor real cambiando los secretos DEPLOY_HOST, DEPLOY_USER, DEPLOY_KEY y DEPLOY_PORT.

6. Automatización con GitHub Actions

El archivo .github/workflows/deploy.yml se ejecuta manualmente (workflow_dispatch) y también al modificar el propio workflow en main, en cuyo caso despliega v1.0.0 automáticamente. Recibe dos parámetros:

ParámetroDescripciónValor por defecto
versionVersión liberada a desplegarv1.0.0
simulate_failureSimula un fallo y ejecuta el rollbackfalse

Pasos del workflow

  1. Preparar el servidor de destino con SSH local e instalar Python, OpenSSH y unzip.
  2. Descargar el ZIP de GitHub Releases con gh release download.
  3. Transferir el ZIP con scp.
  4. Extraerlo en ~/sistema-inventario/version-<versión> con ssh.
  5. Ejecutar el sistema por SSH y verificar la salida esperada.
  6. Si se simula el fallo, comprobar que el error aparezca en la salida.
  7. Si se simula el fallo, provocar el error, recuperar v1.0.0 y verificar.
  8. Publicar las salidas y los ZIP como artefacto de evidencia.

Secuencia de ejecución

9. Preguntas de reflexión

1. ¿Diferencia entre liberar y desplegar? Liberar produce y publica el artefacto versionado; desplegar lo instala, configura y verifica en el entorno de destino.

2. ¿Por qué usar el paquete de RELEASE? Porque es el artefacto oficial y probado; garantiza que se despliega exactamente lo liberado y permite repetir el proceso.

3. ¿Función del entorno de destino? Es donde el sistema se instala y ejecuta para los usuarios; debe cumplir los requisitos y es donde se verifica su funcionamiento.

4. ¿Qué información se necesita para SSH? Host, usuario, llave privada, puerto y llave pública autorizada en el servidor.

5. ¿Por qué usar secretos de GitHub? Para no exponer llaves ni contraseñas en el repositorio o en los logs; se almacenan cifrados y se inyectan en tiempo de ejecución.

6. ¿Ventajas de automatizar? Menos errores manuales, procedimiento reproducible, ahorro de tiempo, evidencia de cada ejecución y rollback consistente.

7. ¿Qué pasa si el destino no cumple los requisitos? El sistema puede no iniciar, fallar al importar módulos, no extraer el paquete o no conectarse por SSH; por eso se comprueban antes de desplegar.

8. ¿Por qué un procedimiento de recuperación? Para volver rápidamente a la última versión estable, reducir el tiempo de inactividad y dejar constancia del incidente.

10. Conclusión

El despliegue manual de v1.0.0 y v1.1.0 funciona correctamente. La automatización con GitHub Actions descarga el artefacto publicado, lo transfiere por SSH, lo extrae, lo ejecuta y verifica, y conserva evidencias. El ejercicio de fallo simulado permitió comprobar que el rollback a v1.0.0 restaura el servicio. El procedimiento queda documentado para que otra persona pueda repetirlo sin depender de los desarrolladores.
